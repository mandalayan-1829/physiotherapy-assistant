### 2.1 Inventory conclusions

* **Orphaned backend endpoints (no frontend consumer):** #11, #13, #17, #29, #30, #31, #32, and `/health` (the client exports `checkHealth()` but never calls it).
* **Frontend calls with no backend endpoint:** **none.** Every path, method, field name and header emitted by `src/services/` matches a real route and schema.
* **Duplicate endpoints:** none. Each route is registered once in `backend/app/main.py`.
* **Inconsistent URL naming:** minor — most routers declare a `prefix`, but `sessions`, `progress`'s parent and `communication`'s routes are registered at the root (`/sessions`, `/messages`, `/alerts`). Functional, but the OpenAPI tags (`communication`) do not match their paths, which will make API9 inventory management harder as the surface grows.
* **Inconsistent request/response shapes:** one instance — `createAlert()` in `src/services/physio.ts:236` is typed `Promise<void>` while the backend returns `201` with an `AlertOut` body. Runtime is harmless (`request()` parses the JSON); the type is simply wrong.
* **Untested endpoints:** #11, #12, #13, #21, #23, #27, #28 (7 of 32).

### 4.1 Mismatches and gaps that are real (not spec drift)

1. **Reports are generated in the browser, not by the backend.** `ReportsView.tsx` and `DoctorDashboard.tsx` call `getMonthlyReports()` / `generateMonthlyReport()` from `src/utils/storage.ts`, which writes to `localStorage` under `physio_monthly_report_drafts`. The backend's `POST /reports/generate` + `GET /reports` are fully implemented and tested but **never called**. `src/utils/storage.ts:97` carries a `TODO(reports)` admitting this.
   *Consequence:* reports are per-browser and per-device, invisible to the clinician, not backed up, and lost when site data is cleared. A doctor signing in on another machine sees an empty report list. This is the single biggest functional gap in the integration.
2. **Progress/history aggregation is client-side.** `GET /progress/daily` is implemented and tested but unused; `ProgressAnalyticsView`, `HistoryView` recompute from the `sessions` array. Consequences: no pagination benefit, and the server's `limit=5000` aggregation logic is dead code.
3. **Safety alerts are double-booked.** `DashboardHome.tsx` and `MedicalProfileView.tsx` call `logGuardianAlert()` (localStorage); `listAlerts`/`createAlert` in `physio.ts` are **exported but never imported**, so `GET/POST /alerts` are unreachable from the UI, and the "Safety & SOS" tab renders `NotImplementedView`.
4. **The doctor cannot reply in a thread.** `App.tsx:handleSendMessage` explicitly refuses for `session.role !== 'patient'` ("requires selecting a patient (not implemented yet)"), even though `POST /messages` supports clinician replies. The backend capability exists; the UI does not expose it.
5. **Report payload shape drift.** Backend `Report.payload` is `{patient_name, patient_email, total_sessions, total_reps, total_duration_sec, avg_form_accuracy, exercise_breakdown, insufficient_data}`. The frontend `MonthlyReport` type expects ~20 different fields (`adherencePercent`, `emailStatus`, `recipients`, `missedSessions`, …). Wiring `GET /reports` will require a mapper — the two models are **not** interchangeable.
6. **`createAlert` return type** is `Promise<void>` but the endpoint returns a body (type-only defect).
7. **Hard-coded `localhost` fallback** in `src/services/api.ts:11`. Safe as a default, but it means a build with `VITE_API_URL` unset will silently point at `http://localhost:8000` in production. See [M8](#medium).

Everything else — URLs, methods, field names, response structure, auth header, token format, role handling — matches. There is **no** "frontend calls an endpoint the backend doesn't have" defect.

| Invalid credentials | ✅ | Uniform `Invalid email or password.` for unknown email, wrong password, inactive account and wrong role |
| Account enumeration — login | ✅ | Identical message + identical counters for unknown addresses |
| Account enumeration — forgot-password | ✅ | `test_nonexistent_email_gets_identical_response_and_no_email`, `test_role_mismatch_is_indistinguishable_from_unknown_email` |
| Account enumeration — **registration** | ❌ | `POST /auth/register` returns **409 "An account with this email already exists."** This is a reliable oracle for "is this address registered?" |
| Session persistence | ✅ | Token in `localStorage`; identity is always re-resolved from `GET /auth/me` (nothing about the user is trusted from storage) |
| Unauthorized / expired / malformed token | ✅ | All → 401 with `WWW-Authenticate: Bearer` (`test_unauthenticated_requests_are_rejected`, `test_invalid_token_is_rejected`) |
| Password change invalidates sessions | ✅ | `token_version` bump; `test_password_change_invalidates_existing_sessions` |
| Failed-login throttling | ✅ | DB-backed, survives restarts, shared across workers (`auth_throttles`) |

**Should authentication stay JWT?** **Yes.** The implementation is correct, stateless, uses a single dependency (`get_current_account`), and already supports global invalidation via `token_version`. Moving to server-side sessions would add Redis/storage requirements and a new failure mode for no security gain at this scale. The two changes worth making are (a) shorter access-token lifetime + a refresh flow, and (b) moving the token out of `localStorage` — both are improvements *within* the JWT design, not a replacement of it.

## 6. AUTHORIZATION / IDOR / BOLA AUDIT (Phase 8)

All patient-scoped reads funnel through `backend/app/services/access.py`:

* `resolve_patient_scope(db, requester, requested_id)` — a **patient** is forced to `requester.id` (or 403 if they name someone else); a **doctor** must supply an id **and** hold an `active` row in `patient_doctor_links`.
* `ensure_patient_access(db, requester, patient_id)` — the same check for non-scoped routes.
* `require_patient` / `require_doctor` — role gates.

Object-level checks exist on `DELETE /diet/{id}`, `DELETE /notes/{id}`, `PATCH /appointments/{id}`, `POST /notes` and `POST /messages`, each comparing the row's owner to the caller.

| Attack scenario | Outcome | Proof |
| --- | --- | --- |
| Patient A reads Patient B's sessions by id | **403** | `test_patient_cannot_access_another_patients_data` |
| Patient A sees B's data in an unscoped list | **empty list** | same test |
| Patient calls a doctor-only endpoint (`/patients`) | **403** | `test_patient_cannot_use_doctor_only_endpoints` |
| Patient writes a note about another patient | **403** | `test_patient_can_only_note_themselves` |
| Doctor reads an unlinked patient | **403**, and `/patients` is empty | `test_doctor_cannot_access_unlinked_patient` |
| Doctor B modifies Doctor A's appointment | **403** | `test_doctor_cannot_modify_another_doctors_appointment` |
| Patient self-approves their own appointment | **403** | `test_patient_cannot_approve_own_appointment` |
| Doctor gains access after a real relationship exists | **200** | `test_doctor_gains_access_after_relationship_is_established` |

**Conclusion: BOLA/IDOR is well handled for patients and for cross-doctor writes.** Four residual issues:

* **H6 — cross-clinician note exposure.** `note_service.list_notes` filters only on `patient_account_id`, so **Doctor A can read clinical notes authored by Doctor B** for a shared patient. `communication_service.list_messages` *does* filter by `doctor_profile_id`; `notes` is inconsistent with it. Decide whether shared-patient note visibility is intended (it may be clinically desirable) and encode the decision explicitly.
* **M4 — every clinician profile is readable by every authenticated user.** `list_doctor_profiles` ignores the requester and returns all rows, including `email`, `whatsapp` and `contact` for clinicians the patient has no relationship with. Directory-by-design, but it is an unnecessary contact-detail disclosure to any logged-in user.
* **M5 — patients silently create the authorization link.** `create_appointment` calls `ensure_link`, so booking a checkup grants that clinician ongoing read access to the patient's entire record, with no clinician-side acceptance step and no way for the patient to revoke it in the UI. There is also no cap on how many clinicians a patient can link to.
* **M6 — `GET /doctors` no longer exists as a public route** but `/doctors/{id}` has no relationship check, so any authenticated user (including a patient) can enumerate `id=1..N` and harvest the whole clinician directory one row at a time.

No endpoint relies on frontend route guards. Deny-by-default holds.

## 8. DATABASE AUDIT (Phase 10)

**Alembic is confirmed as the migration system** (`backend/alembic.ini`, `backend/alembic/env.py` reading `DATABASE_URL` from app settings — so migrations and the API always target the same database). Two revisions exist: `c4c7db25443c` (initial, 10 tables) → `b0411f7bc699` (reset tokens + throttles + `token_version`).

### 8.1 Schema quality

* **Foreign keys:** correct and complete, with deliberate `ondelete` semantics — `CASCADE` for patient-owned data, `SET NULL` for `doctor_profiles.account_id` (preserves directory-only clinicians) and for `doctor_notes.doctor_profile_id` (a note survives if a clinician account is removed).
* **Indexes:** every FK used in a `WHERE` is indexed; `accounts.email` is unique+indexed; `workout_sessions.performed_at`, `diet_records.recorded_at`, `appointments.status` carry their own indexes. No obvious missing index.
* **Unique constraints:** `accounts.email`, `patient_profiles.account_id`, `doctor_profiles.account_id`, `patient_doctor_links(patient_account_id, doctor_profile_id)`, `auth_throttles(scope, key)`. Good.
* **Naming convention** is centralised in `db/base.py` (`NAMING_CONVENTION`) — migrations will stay deterministic.
* **Timestamps:** `created_at` everywhere (server default); `updated_at` only on `accounts` and `patient_profiles`.
* **Soft delete:** none. Deletes are hard (`DELETE /diet/{id}`, `DELETE /notes/{id}`). No `deleted_at`/`is_deleted` anywhere.
* **Relationships:** only `Account`↔profiles are ORM-mapped. Other tables are queried with explicit `select()` statements, so **there is no N+1 risk** from lazy loading. `doctor_service.list_doctor_profiles` is the one O(n) query-in-loop (`link_exists` per clinician) — fine at directory scale, should become a single `join` beyond ~100 clinicians.
* **No plaintext sensitive data:** passwords are bcrypt; reset codes are bcrypt; nothing is stored encrypted-at-rest beyond that (patient health fields are plaintext — needs disk-level encryption in production, see Phase 20).

### 8.2 Findings

* **C3 — migration `b0411f7bc699` will fail on a non-empty database.** `op.add_column('accounts', sa.Column('token_version', sa.Integer(), nullable=False))` adds a `NOT NULL` column with **no `server_default`**. On PostgreSQL (and SQLite) this errors with *"column contains null values"* the moment `accounts` has rows. It passes locally only because dev DBs are recreated empty. **Fix:** `server_default="0"`, and keep the server default (or drop it in a follow-up migration) so the column stays valid for existing rows.
* **M3 — `reports` has no unique constraint on `(patient_account_id, month_key)`.** `report_service.generate_report` does a read-then-write check, which is racy: two concurrent `POST /reports/generate` calls for the same month can produce duplicate rows. Add a unique constraint and `ON CONFLICT`-style upsert.
* `appointments.date` / `.time` and several `PatientProfile` date fields are `String`, not `Date`/`Time`. `AppointmentCreate` only enforces `min_length`, so arbitrary text ("tomorrow morning") is storable, which will break date filtering and report bucketing.
* `patient_profiles.age` is nullable while every other numeric field is `NOT NULL DEFAULT`. Minor inconsistency.
* `Report.payload` is schemaless `JSON`; combined with the frontend/backend shape drift in [4.1(5)](#41-mismatches-and-gaps-that-are-real-not-spec-drift), it will drift further without a versioned payload shape.
* No retention/cleanup job for `auth_throttles` (grows forever), `password_reset_tokens` (one row per request, `invalidated` rows never pruned), or consumed reset rows.
* `auth_throttles.key` stores patient **email addresses** in the clear for rate-limiting purposes — a minor privacy consideration.
* The Alembic `downgrade()` paths drop whole tables without guarding data loss. Acceptable for a pre-production project, but never run them in production.

### 9.2 Verdict on the preferred architecture

```
Camera → local/on-device processing → exercise metrics → backend → minimal storage
```

**The runtime privacy model is correct and should be preserved:**

* ✅ **No raw video is ever uploaded.** `PoseTracker.tsx` calls `getUserMedia` and renders frames to a `<canvas>`; the only network call in the whole frontend is `fetch()` inside `src/services/api.ts`. Frames never leave the device, and the camera stream is stopped on unmount (`streamRef.current.getTracks().forEach(t => t.stop())`).
* ✅ **No pose landmarks are persisted.** `POST /sessions` accepts only aggregate metrics (reps, accuracy %, duration, notes) — the `WorkoutSessionCreate` schema has no landmark field. The loopback/tasks model therefore already matches the preferred architecture.
* ✅ **No health data is sent to any third party.** No AI API, no analytics, no error reporting, no ad SDK.
* ✅ **No tracking cookies or third-party scripts** in `index.html`.

**Privacy defects:**

* **C1 — the entire legacy database is committed to git.** `aiphysio.db` is tracked (`git ls-files` confirms) and lives in three commits. It contains one `users` row with name, age, email, DOB, contact number, occupation, blood group, height, weight, medical conditions, current medications, allergies, precautions, pain profile and surgical history — plus an **unsalted SHA-256 password digest**. `guardian_alerts`, `appointments` and `diet_log` tables are also present. If this repository has ever been public (or shared), this is a disclosure of identifiable health data.
* **H5 — the production reset-code path can leak codes into server logs.** The `console` transport deliberately logs the full message body, including the 6-digit code, with a `EMAIL NOT SENT` warning. That is correct for local development, but if the backend is deployed with `EMAIL_BACKEND=auto` and no `SMTP_HOST` set, the transport silently becomes `console`, the code lands in the platform's log stream, and **no email is delivered** — so users cannot reset at all while their codes sit in logs.
* **M7 — no retention policy, no audit trail, and consent fields were dropped.** Nobody can answer "who accessed this patient's record, and when?" — the app has no access log. Rehab notes and messages are kept indefinitely. The legacy `users` table has a `consent_given` column that the new `patient_profiles` deliberately does not; for health data this is worth re-adding.
* **L2 — PII in logs.** Successful reset delivery logs the recipient address; failed SMTP delivery logs the exception string. No tokens or passwords are logged outside the dev console transport.
* No data-export or account-deletion path exists, which health-data regimes generally require.

## 12. FILE UPLOAD / REPORT SECURITY (Phase 14)

**There is no file handling in the application.** No upload endpoint, no `UploadFile`/`File`/`Form` parameter, no storage bucket, no static file mount, no signed or public URLs, and no user-supplied filename — so the entire upload attack class (extension/MIME bypass, traversal, malware, public-bucket exposure) **does not currently apply**.

Consequences worth noting:

* The project lists `python-multipart==0.0.20` in `backend/requirements.txt`, and that package carries **11 advisories** (see [Phase 18](#18-dependency-security-phase-18)). It cannot be removed outright — FastAPI imports it for any form/file route — but since no such route exists, exposure is near zero. Upgrade it anyway.
* "Reports" in this app are **JSON aggregates**, not files. They are returned inline, authorized per patient, and never written to a public location. The only residual reporting risks are the authorization check (present and tested) and the missing unique constraint (M3).
* If uploads are added later (e.g. imaging or a profile photo), the checklist is: allowlist extensions **and** sniff content, cap size, generate server-side filenames, store outside the web root, serve through authorized/signed URLs, scan for malware, and define retention.

## 13. RATE LIMITING / RESOURCE PROTECTION (Phase 15)

Recommended limits, derived from what these endpoints actually do:

| Endpoint | Current | Recommended | Rationale |
| --- | --- | --- | --- |
| `POST /auth/login` | 5 failures / 15 min **per email** | Add **per-IP** (e.g. 20/15 min) and a global cap | Blocks distributed credential stuffing; per-email alone is trivially bypassed by rotating addresses |
| `POST /auth/register` | **none** | 5 / hour per IP; 1 / minute burst | Registration writes 2 rows and is fully unauthenticated. Also the account-enumeration oracle |
| `POST /auth/forgot-password` | 60 s cooldown + 5/h per email | Keep, add 20/h per IP | Protects the mail provider's reputation and your costs |
| `POST /auth/verify-reset-code` | 5 attempts per token row | Keep; add 20/hour per email+IP | Prevents 6-digit brute force across many reset rows |
| `POST /auth/reset-password` | per-token | 10/hour per IP | Cheap, but unbounded |
| `POST /reports/generate` | **none** | 10/hour per patient | Currently loads **every** session a patient owns and recomputes — the most expensive unauthenticated-adjacent write path |
| `POST /appointments` | none | 10/hour per patient | Prevents booking spam and `patient_doctor_links` inflation |
| `POST /messages` | none | 60/hour per account | Prevents chat spam |
| `POST /alerts` | none | 20/hour per patient | Prevents alert flooding |
| Expensive AI/pose operations | **N/A** | — | No server-side AI/pose work exists; pose math runs in the browser. **If real on-device inference is added, keep it client-side** — there is then no server CPU to protect, which is exactly why the current design needs no expensive-operation limiter |

**Redis:** **not required now.** The `auth_throttles` table already provides correct, restart-surviving, shared counters — the same property Redis in-memory counters would give — as long as a single database backs all instances. Introduce Redis (or a managed rate-limiter) only if you scale to multiple backends **and** the extra DB write per throttled request becomes measurable, or if you need sub-millisecond counters. Do not add it pre-emptively.

## 14. THIRD-PARTY SERVICE ALTERNATIVE ANALYSIS (Phase 16)

There is **nothing to replace**: the project consumes no external API. Two forward-looking decisions are worth recording anyway.

### 14.1 Password-reset email delivery (the only service this project genuinely needs)

The backend already abstracts delivery behind `EmailSender` with an `smtp` and a `console` implementation, so *any* provider works without touching business logic.

| Option | Security | Free tier / cost | Reliability | DX | Lock-in | Verdict |
| --- | --- | --- | --- | --- | --- | --- |
| **Any SMTP provider via the existing `SmtpEmailSender`** | TLS (`STARTTLS`), credentials from env, no hardcoding | provider-dependent | good | **already implemented** | none beyond the provider | ✅ **Recommended** — zero code change |
| **Resend** (developer-first transactional email API) | API key (server-side only), verified domain | free tier for low volume | high, good deliverability | very fast (`RESEND_API_KEY`, one SDK call) | low | ✅ Good alternative if SMTP deliverability proves fiddly; requires adding a transport class |
| Self-hosted Postfix/relay | full control, no third party sees the message | free (infrastructure only) | **deliverability risk** — self-hosted mail is frequently spam-filtered | high operational cost | none | ❌ Not worth it for password resets |
| Keep `console` transport in production | leaks the code into logs and delivers nothing | free | **broken product** | – | – | ❌ **Forbidden** (see H5) |

**Recommendation:** configure **one** SMTP provider using the existing settings (`EMAIL_BACKEND=smtp`, `SMTP_HOST/PORT/USERNAME/PASSWORD/FROM_EMAIL`), and set `EMAIL_BACKEND=smtp` explicitly rather than relying on `auto`, so a missing configuration fails loudly instead of silently degrading to the console transport. Add Resend only if deliverability becomes a problem.

### 14.2 Real pose estimation (if/when the simulated tracker is replaced)

## 19. FINDINGS INDEX

Severity is assigned by real exploitability and business impact in *this* application, not by generic CVSS.

<a id="critical"></a>
### CRITICAL

**C1 — The legacy database `aiphysio.db` is committed to git (and present in history).**
*Evidence:* `git ls-files aiphysio.db` → tracked; `git log --oneline -- aiphysio.db` → 3 commits (`7b35e9f`, `ea2a631`, `912e837`). The file contains a `users` table (1 row) with name, age, email, DOB, contact number, occupation, blood group, height, weight, medical conditions, medications, allergies, precautions, problem/pain/surgical history, plus an **unsalted SHA-256 password digest**; also `doctors` (2 rows with contact/WhatsApp/email), `appointments` (1), `diet_log` (1).
*Impact:* Identifiable health data and a crackable credential digest are in the repository and every clone/fork. If the repo is or was ever public, treat it as a data disclosure.
*Fix:* (1) `git rm --cached aiphysio.db`; (2) add `*.db` / `aiphysio.db` to `.gitignore`; (3) **rewrite history** (`git filter-repo` or BFG) and force-push, or — if that is unacceptable — treat the data as disclosed and rotate the affected credentials; (4) require the affected user to reset their password; (5) in future, load legacy data via `backend/scripts/migrate_legacy.py` from a path **outside** the repo.
*Note:* the legacy DB is still needed for `migrate_legacy.py`. Keep it locally, excluded from git — do **not** delete it.

**C2 — Insecure default JWT signing key with no startup validation.**
*Evidence:* `backend/app/core/config.py:31` → `secret_key: str = "dev-insecure-change-me"`. `backend/app/core/security.py` signs and verifies every token with `settings.secret_key`. Nothing checks that it was changed.
*Impact:* Deploying without setting `SECRET_KEY` means **anyone can mint a valid JWT** for any `sub` and any `role` — complete authentication bypass, including doctor-level access to every patient.
*Fix:* Validate at startup and refuse to boot if `secret_key` is the default or shorter than 32 bytes; add the generated value to the deployment environment (`python -c "import secrets; print(secrets.token_urlsafe(48))"`); document it in the README and the deploy checklist.

**C3 — Migration `b0411f7bc699` fails on a non-empty database.**
*Evidence:* `op.add_column('accounts', sa.Column('token_version', sa.Integer(), nullable=False))` — no `server_default`, no backfill.
*Impact:* `alembic upgrade head` errors ("column contains null values") on any database that already has accounts, blocking the first production deploy or any migration of real data.
*Fix:* `sa.Column('token_version', sa.Integer(), nullable=False, server_default='0')`, then optionally `op.alter_column(..., server_default=None)` in a follow-up. Re-test against a PostgreSQL instance seeded with an account row.

**C4 — The "AI pose tracking" feature is a simulation; the camera feed is never analysed.**
*Evidence:* `src/components/PoseTracker.tsx` calls `getUserMedia` only to display the video, then every frame runs `generatePoseLandmarks(exercise.id, phase)` — a hand-written trigonometric model that fabricates 33 landmarks. No pose model, no `@mediapipe/*`, no `@tensorflow/*` package exists in `package.json`; the only MediaPipe code in the repo is in the unused legacy `core/`.
*Impact:* The product's headline capability does not work. Rep counts, form errors and accuracy percentages are synthetic and are then persisted as if they were real clinical measurements — which is both a functional and a clinical-integrity problem. UI copy (`AccountProfileModal.tsx:321`: *"using MediaPipe kinematics"*; `PortalAuth.tsx`: *"AI camera-guided exercise form & repetition counter"*) and `metadata.json` (`MAJOR_CAPABILITY_SERVER_SIDE_GEMINI_API`) overstate this.
*Fix (choose one, explicitly):* (a) implement real on-device pose estimation with MediaPipe Tasks / TF.js MoveNet — see [14.2](#142-real-pose-estimation-ifwhen-the-simulated-tracker-is-replaced); or (b) relabel the feature honestly as a guided/simulated practice mode and stop persisting its output as clinical accuracy. Do not deploy the current state while presenting synthetic data as measured rehabilitation performance.

<a id="high"></a>
### HIGH

**H1 — Account-level self-registration as a doctor (OWASP API6).** `POST /auth/register` accepts `role: "doctor"` from anyone; `specialization` may be any string and `license_number` is accepted and discarded. A new doctor account appears in every patient's directory and becomes a fully linked clinician the moment a patient books them.
*Fix:* add an `is_verified` gate that keeps an unverified clinician out of `/doctors` and unable to be booked; persist and review credentials (or issue invite codes). Until then, treat every doctor account as untrusted.

**H2 — No rate limiting on registration; login throttling is per-email only.** Registration is unauthenticated and unlimited. Login/reset counters are keyed by email, so rotating addresses (or distributing across IPs) bypasses them entirely.
*Fix:* per-IP limits on `/auth/register`, `/auth/login`, `/auth/forgot-password`, `/auth/verify-reset-code`; see the table in Phase 15.

**H3 — Per-email throttling enables account enumeration *and* targeted lockout.** Because the counter is keyed by the submitted email, an attacker can lock a known victim out (denial of service) while probing unknown addresses for free.
*Fix:* combine per-account and per-IP counters, add exponential backoff, and add a CAPTCHA/proof-of-work after repeated failures.

**H4 — Known vulnerabilities in two backend dependencies**, one of them in the authentication path (`PyJWT 2.10.1` → 10 advisories; `python-multipart 0.0.20` → 11 advisories, currently unreachable). See Phase 18.

**H5 — Password reset can silently leak codes into production logs and deliver nothing.** With `EMAIL_BACKEND=auto` (the default) and no `SMTP_HOST`, the console transport is selected, which logs the full message **including the 6-digit code** and returns `delivered=False`. The reset response is still the generic success message.
*Fix:* set `EMAIL_BACKEND=smtp` explicitly in production and validate the SMTP configuration at startup so the console transport can never be selected outside development.

**H6 — Cross-clinician note exposure (OWASP API1/API3).** `note_service.list_notes` filters only by `patient_account_id`, so any doctor linked to a patient can read notes written by *other* clinicians, including the authoring `doctor_profile_id` — while `messages` correctly filter by clinician. Decide and enforce the intended visibility.

<a id="medium"></a>
### MEDIUM

**M1 — Unbounded work on `/reports/generate`.** Loads **every** session a patient owns (no month filter in the query, filtering happens in Python) and recomputes the breakdown, unauthenticated-limited. *Fix:* filter by month in SQL and add a per-patient limit.

**M2 — 7-day tokens, no refresh, no true logout.** A stolen or leaked token is valid for a week; `/auth/logout` is a no-op and there is no revocation list (only the blunt `token_version` bump). *Fix:* shorten the access-token lifetime, add refresh tokens, and consider moving to httpOnly `Secure` cookies.

**M3 — `reports` lacks a unique constraint on `(patient_account_id, month_key)`**; the read-then-write upsert is racy. *Fix:* unique constraint + conflict-safe write.

**M4 — The full clinician directory (including email/WhatsApp) is visible to every authenticated user** (`list_doctor_profiles` ignores the requester). *Fix:* expose only the fields a directory needs, and paginate.

**M5 — Booking silently grants permanent record access.** `create_appointment` → `ensure_link` gives the clinician read access to the patient's whole history with no consent step, no clinician acceptance, and no revocation path in the UI. *Fix:* make linkage explicit, time-boxed or revocable, and show the patient who can see their data.

**M6 — No relationship check on `GET /doctors/{doctor_profile_id}`.** Any authenticated user can enumerate ids and harvest the directory one row at a time.

**M7 — No access audit log, no retention policy, no consent record; hard deletes everywhere.** There is no way to answer "who viewed this patient's record, when?" *Fix:* append-only access log, documented retention, optional consent flag (the legacy schema had one).

**M8 — `http://localhost:8000` is the silent fallback for `VITE_API_URL`.** A production build with the variable unset will point every browser at its own localhost. *Fix:* require the variable at build time (throw if missing) instead of defaulting.

**M9 — No frontend lockfile for tooling.** `npm audit` cannot run (`ENOLOCK`); `bun` is not installed here. Frontend CVE status is unknown and builds are not reproducible. *Fix:* commit `package-lock.json` (or standardise on bun and use `bun audit`), then run the audit before deploying.

**M10 — No security headers, and API docs are public.** *Fix:* add a headers middleware (HSTS, `X-Content-Type-Options: nosniff`, CSP, Referrer-Policy) and set `docs_url=None, redoc_url=None, openapi_url=None` in production (the `test_openapi_schema_is_served` test will need an environment guard).

**M11 — No request-size limits, and free-text fields have no `max_length`.** `NoteCreate.note_text`, `MessageCreate.message`, `AppointmentCreate.reason`, `AlertCreate.message` accept unlimited strings. *Fix:* `max_length` on the schemas plus a body-size limit at the proxy.

## 22. FINAL GO/NO-GO

### Integration (frontend ⇄ backend)

> ## `READY FOR INTEGRATION` — with named caveats

**Evidence for "ready":**
* Every URL, HTTP method, request field, response shape, auth header and error key emitted by `src/services/` matches the Pydantic schema and FastAPI route that serves it — verified endpoint by endpoint (Phase 6). **Zero** calls to non-existent routes and zero field-name mismatches.
* Authentication is fully wired and server-verified: register/login/logout/me plus the complete three-step reset flow, with `localStorage` holding only the token and identity always re-fetched from `GET /auth/me`.
* `204`, error bodies and the five server-provided error extras (`failed_attempts`, `show_forgot_password`, `retry_after_seconds`, `restart_required`) are all handled correctly.
* The base URL is environment-driven (`VITE_API_URL`); nothing is hardcoded per call site.
* The backend boots, creates its schema, and passes 58/58 tests.
* The frontend type-checks and builds cleanly.

**Caveats (integration is possible, but these features will not work as users expect):** monthly reports, progress/history analytics, and safety alerts are computed/stored in the browser (Phase 6 §4.1 items 1–3); doctors cannot reply in a thread (item 4); and the pose-tracking capability is simulated (C4). Wiring these is straightforward and requires no architectural change — and the backend endpoints already exist and are tested.

### Deployment

> ## `NOT READY FOR DEPLOYMENT`

**Concrete blockers, all reproducible:**
1. The public JWT signing key default (`config.py:31`) — deploying as-is permits a complete authentication bypass. (C2)
2. `aiphysio.db` is committed with identifiable health data and an unsalted password digest, and it is in git history. (C1)
3. Alembic revision `b0411f7bc699` will fail the moment `accounts` is non-empty. (C3)
4. A headline product capability (AI pose analysis) does not exist and its synthetic output is stored as clinical measurement. (C4)
5. Anyone can self-register as a doctor and be booked by a patient. (H1)
6. There is no email provider, so password reset either delivers nothing or leaks the code into logs. (H5)
7. Two backend dependencies carry advisories, one on the authentication path. (H4)
8. Frontend dependency security is unauditable (no lockfile). (M9)
9. No HTTPS, managed PostgreSQL, backups, CORS origin list, security headers, or CI are configured; and it is still unconfirmed whether the deployed Vercel project even points at this application's root. (§17–18)

**What is genuinely good and should be protected during the fixes:** the authorization layer (`access.py` + the 8 isolation tests) is the strongest part of the codebase; there are **no API keys or third-party services** to leak or rotate; no raw video or pose landmarks ever leave the browser; and the test suite is meaningful, isolated, and green. This is a solid foundation being held back by a small number of specific, fixable defects — not by its architecture.

**Recommended immediate next actions:** Stage 0 items 1–6 in §20. They are self-contained, low-risk, and clear three critical blockers without changing a single line of application logic.
